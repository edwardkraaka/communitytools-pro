## The prompt (verbatim)

You are doing deep security research for an AUTHORIZED penetration-testing program (professional security firm, signed rules of engagement). This is pure web research on public information: do not send emails or messages, interact with third parties, or create accounts on my behalf. Return your findings as a comprehensive markdown digest in your final reply (the inline digest is the deliverable; only create files if a section demands it).

GOAL: I am retooling the program's testing methodology from a traditional OWASP-top-10 breadth model ("scan and checklist") toward how specialized vulnerability researchers, zero-day hunters, and blockchain exploit analysts actually work. I need a standing intelligence digest — structured, dense, machine-consumable (an LLM agent will read it as its knowledge base) — covering what is CURRENT as of September 2026. Prefer 2025–2026 sources; include older material only where it remains the canon. Cite URLs inline. Use tables wherever possible. No filler, no disclaimers beyond the authorization framing above.

Produce these six sections:

## 1. LIVE INTELLIGENCE SOURCES — continuously-updated repositories of new CVEs / exploits / attack intel
For each source: name • URL • what it carries • update cadence • access method (web / RSS / git clone / API — give the exact endpoint or clone URL) • signal quality (speed + reliability) • how a program could poll it daily. Cover at minimum: CISA KEV, NVD API 2.0, GitHub Security Advisories + the github/advisory-database repo, nomi-sec/PoC-in-GitHub and similar PoC aggregators, Exploit-DB, Packet Storm, Project Zero's 0day-in-the-wild tracker, osv.dev, GitLab Advisory, Vulners, Sonar (Semmle) advisories, vendor PSIRT feeds (Microsoft, Apple, Adobe, Ivanti, Fortinet, Palo Alto, Citrix, Atlassian), ProjectDiscovery nuclei-templates feed, and obscure-but-high-signal sources (regional CERTs like JPCERT/CC, SSD Secure Disclosure, patch-diffing blogs/newsletters, vulnerability-monitoring feeds). Include the gray-but-public markets (e.g., 0day.today, exploit.in) with an explicit caution note on provenance/legality — awareness only. Also cover the 2025–2026 AI-originated research and tooling feeds (AISLE disclosed findings, XBOW's published case write-ups, OpenAI Daybreak research) with the same per-source fields, noting that LLM-research methodology tracking lives in Section 5 so these rows focus on where their findings surface. Finish with a "public PoC hygiene" subsection on poisoned and junk proof-of-concepts: backdoored PoC repositories targeting security toolchains (e.g., the ChocoPoC campaign) and measured malicious-PoC rates from peer-reviewed research (e.g., the USENIX WOOT SecurePoC study), with operational OPSEC rules for handling collected PoC code. Then a ranked TOP 10 for a program whose targets are web applications, APIs, and blockchain/crypto companies (the AI-research feeds sit outside this operational ranking by design — research-watching, not daily polling).

## 2. RECENT BLOCKCHAIN HACK ANATOMY (2024–2026)
Pick 15–20 significant incidents (exchanges, bridges, lending protocols, wallet infrastructure, custodians, mining pools, on-chain analytics firms). For each: date • victim type • root-cause CLASS • THE UNCONVENTIONAL ENTRY VECTOR — specifically how it was actually done, which is almost never "scanner found a CVE": dev-tooling supply-chain compromise, browser-side transaction-signing malware, social engineering of employees/L1 support, key-management/MPC-infrastructure compromise, oracle/price-feed manipulation, compiler or runtime bugs, flash-loan-amplified logic bugs, malicious or compromised dependency in the shipped wallet app, front-end/CDN compromise, insider action • impact in USD • whether the precursor was remotely observable from OUTSIDE (leaked keys in npm/git, exposed admin panels, vulnerable dependency shipped in the wallet, seed-phrase exposure, unprotected key-holder infra) • a one-line "what an authorized external tester could have caught in advance." Use rekt.news, SlowMist Hacked, PeckShield post-mortems, Immunefi, official disclosures, credible journalism. Additionally include a SEPARATE key-generation and classical-cryptanalysis subsection (2022–present, outside the main case count and taxonomy — root cause is weak key generation or vintage cryptography, not operational compromise): the Profanity/vanity-generator seed failure (2022, incl. Wintermute), Milk Sad / Libbitcoin `bx seed` (CVE-2023-39910, 2023), Randstorm / BitcoinJS-era browser wallets (2023), predictable-key harvesting (Ethercombing / Blockchain Bandit, incl. the December 2024 consolidation), residual weak-entropy key exposure reporting, and the 2026 Coldcard seed-entropy incident — same per-incident fields (date • victim type • root-cause class • entry vector and impact • outside precursor / what an authorized tester could have caught). End with: (a) a taxonomy table of entry-vector classes ranked by frequency AND by USD lost; (b) the top 10 remotely-observable precursors ranked by how often they preceded real incidents.

## 3. FRESH / OBSCURE CVE CLASSES HITTING WEB & CRYPTO INFRA (2025–2026)
What is ACTUALLY being exploited in the wild against web apps, APIs, and crypto-company infrastructure (skip ICS/automotive/telecom): recent KEV entries affecting web stacks; CI/CD supply-chain incidents (e.g., the tj-actions/changed-files GitHub Actions compromise, npm/PyPI campaigns against crypto dev tooling, typosquatting); auth-bypass CVEs in common frameworks; exposed Grafana / Kubernetes dashboard / Redis / Postgres / Airflow patterns; API-gateway pitfalls; LLM-application CVEs (server-side prompt injection, model-registry poisoning, agentic-tool hijacking); SSRF-to-cloud-metadata chains that worked. For each: CVE ids or incident name • detection signature — what in a target's PUBLIC surface reveals exposure • a one-line safe verification probe an authorized tester would use • exploitability constraints. Also list the most impactful exploited vulnerabilities of 2025–2026 overall.

## 4. ZERO-DAY HUNTER METHODOLOGY — the specialized way bugs are actually found
How professional researchers and top bug-bounty hunters find NOVEL bugs (not scanner findings): target selection and ecosystem-impact reasoning; surface triage; version/patch diffing (obtaining patched vs unpatched artifacts, deriving the fixed bug, turning a 1-day into fresh 0-days — cite the canonical public writeups); reading shipped JavaScript, source maps, and minified bundles for logic and secrets; auth-flow analysis (session, token, OAuth scope) as highest-yield surface; fuzzing strategy (what to fuzz, harness building, sanitizer choice, triage at scale); variant analysis after a new bug class lands; verification and PoC discipline. Name the public methodologies, blogs, and trainings that are REAL canon (Project Zero writeups, SSD, public hunter playbooks, recon/diff automation pipelines). Include how top hunters structure automation (recon pipelines, watch triggers, diff alerts).

## 5. LLM-DRIVEN SECURITY RESEARCH — 2025–2026 state of the art
How teams use LLMs to find REAL bugs: Google Project Zero's Big Sleep finding its first true zero-day (and what followed); XBOW topping HackerOne leaderboards; the Naptime/Big Sleep methodology; OSS-Fuzz LLM integrations; variant analysis with LLMs at scale; agentic harnesses for finding logic bugs. Be specific about which bug CLASSES LLMs are demonstrably good at (logic bugs, auth flows, patch-diff/variant triage) versus where humans still dominate (novel memory corruption, architectural reasoning). Conclude with what an LLM-agent-driven authorized-pentest program should copy from these results — concrete practices (always diff the patch, always read the target's shipped JS bundles, hypothesis-led experiments before breadth scanning, adversarial self-validation).

## 6. SYNTHESIS — threat-intel-first testing program design
Given all the above: propose in bullet form how an authorized-pentest program for web + crypto targets should structure a "threat-intelligence-first" phase: what to check per-target BEFORE generic scanning, in what order (org fingerprint → stack version match → known-exploit pattern match → leaked-credential surface → hypothesis list), what triggers deep dives, and how to keep the intel base current (polling cadence + automation hook per source from Section 1). Format it as a decision procedure an LLM testing agent could follow literally.
