# Wallet-Generator PRNG Vintage

## When this applies

- Client wallet keys were generated by 2011–2023 consumer tooling and you need to know whether the keys themselves (not the passphrase, not the storage) are guessable — during key-management code review, treasury screening, or an engagement that inherits legacy wallet infrastructure.
- The tooling vintage: Profanity (Ethereum vanity generator, 2022), BitcoinJS/browser wallet libraries of the 2011–2015 era ("Randstorm" class), Libbitcoin Explorer 3.0.0–3.6.0 (`bx seed`, CVE-2023-39910, exploited in the wild 2023), Trust Wallet browser-extension key creation (2022–2023 window), RoboForm-generated passwords before 7.9.14 (2015).
- Trigger phrases: "vanity address", "keys generated in a browser in 2013", "bx seed", "we used an old online generator".
- This is the software-wallet sibling of `scenarios/weak-rng/bip39-seed-entropy.md` (hardware-wallet seed space) — the failure is enumerable seed material at keygen, and entropy added later does not repair it.

## Technique

Three recurring vintage patterns:

1. **Small seed expanded to full width.** Profanity seeded 256-bit key generation from a random 32-bit value: the entire user-visible keyspace was 2^32 per installation. Vanity addresses make the exposure self-announcing — the address format itself advertises membership in the weak set, and the on-chain set is public.
2. **Time-seeded PRNG.** Milk Sad (Libbitcoin `bx seed`): the 32-bit value came from system time regardless of the requested entropy width, so every mnemonic maps to a timestamp — sweepable by enumerating a wall-clock window. Randstorm (BitcoinJS era): a library probed `window.crypto.random`, hit a type-comparison error in browsers that lacked it, silently fell back to `Math.random()` plus the millisecond timestamp fed into an RC4/Arcfour pool; on the order of 1.4M wallets across ~16 services were reported at risk.
3. **Predictable key ranges harvested at scale.** "Ethercombing"/Blockchain Bandit: keys from broken or user-chosen tiny ranges are swept continuously by bots. Reported ~732 guessed keys since 2016; on 2024-12-30 one actor consolidated 51,000 ETH from ten wallets that had been dormant since 2023-01-21 (reported ~$172M).

Common thread: at-the-moment-of-keygen entropy defines the floor. Later hashing, derivation, or mnemonic encoding over it adds structure, not entropy.

## Steps

### 1. Establish tooling provenance

Identify which tool and version created the keys — shipped JavaScript or firmware archaeology, package-lock snapshots, wallet file metadata, client interviews, on-chain address formats (vanity prefixes, derivation-path fingerprints per BIP-44/49/84 account look). This decides which vintage pattern applies.

### 2. Bound the generation window

Use the address's first on-chain activity (first deposit/first sweep) as an upper bound; client events (device purchase, account creation) as lower bounds. For time-seeded generators this window *is* the keyspace.

### 3. Model and regenerate candidates

Reproduce the generator: same PRNG (MT19937 for `bx seed`, RC4/Arcfour pool for the BitcoinJS class), same seeding input (unix/epoch time candidates across the window). The public Randstorm reconstruction repo regenerates candidate seeds on the order of 1.4B per two-week window — that is the scale a correct model reaches.

### 4. Derive addresses and screen

For each candidate seed, derive the same key material the tool would have, then compare against the target address set. At scale, hash candidates into a Bloom filter of known-funded addresses first, confirm positives exactly (the pattern used in `scenarios/weak-rng/bip39-seed-entropy.md` — reuse its sweep harness).

```python
# sketch: time-seeded candidate sweep
from mnemonic import Mnemonic  # or the tool's own derivation library
target_filter = load_bloom("funded_addresses.bloom")  # built from client/watched addresses
for ts in range(t_start, t_end, 1000):        # ms or s resolution per the tool
    seed_bytes = model_generator(ts)           # MT19937/RC4 reproduction
    for acct in range(salt_iterations := 10):  # per-tool iteration count
        addr = derive_address(seed_bytes, acct)
        if target_filter.contains(addr):
            confirm_exact(addr, seed_bytes, ts)  # disk-backed confirm, log candidate
```

### 5. Report vintage exposure

Deliverable is the exposure finding: which keys are in a computable set, the window and keyspace size, reproduction evidence from a lab-generated fixture, and a migration recommendation (regenerate with a modern generator, move funds once, retire old addresses). Stop at proof — sweeping or moving client funds is out of scope for a test engagement.

## Verifying success

- A lab fixture (key generated with the same tool at a known time) is recovered by the sweep end-to-end.
- Derived candidate addresses match the real target addresses exactly on confirmation.
- Screening reproduces published weak-cluster hits (Profanity address lists, Milk Sad disclosures) — sanity check for the model.

## Common pitfalls

- Assuming mnemonic word count or SHA-256 masking adds entropy (see `scenarios/weak-rng/bip39-seed-entropy.md`).
- Conflating key-generation entropy with RFC 6979 deterministic-nonce behavior — nonce determinism is the `scenarios/signature-forgery/ecdsa-nonce-reuse.md` family, a different bug.
- Trusting "modern" labels: the July 2026 Coldcard incident (build misconfiguration disabling the hardware TRNG) shows current tooling fails too — audit, don't assume vintage.
- Forgetting that first-activity timestamps bound the sweep window; without them the search is unbounded.
- Sweeping funds as "proof" — report the finding, let the client act.

## Tools

- `mnemonic` / `bip_utils` for BIP-39/32/44 derivation reproduction.
- Bloom filters (`pybloom_live`) or a hash-set for the funded-address screen.
- Chain explorers / local index for first-activity timestamps and funded sets.
- Public reconstruction repos as references (e.g., the Randstorm community repo) — study them in a disposable VM; see the PoC-hygiene guidance in `../../../../threat-intel/reference/intel-sources.md`.
- [weak-kdf-vintage.md](../kdf/weak-kdf-vintage.md) — when the generator was fine but the derivation (vault, `wallet.dat`) is the weak layer.
